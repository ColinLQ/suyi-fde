## 补货深度分析（第2.5步，净缺口×季节×地区）

> 背景：alert-rules 的建议补货量有两大盲区——①不扣除已在生产的订单（直接下单会重复补）；②基于30日均值，在换季节点严重滞后。本步交叉衣者在产订单+多客season字段+订单收件地域，给出可直接执行的补货动作。

**净缺口公式**：`净补 = max(0, 建议补货量 − 该款在产订单plan_total_num合计)`；建议 ≤ 在产 → 只需催货。在产数据源 `yizhe_production_list.jsonl`（day.extra），`stock_out_num>0` 部分已在途，标注出来供到货预期参考。

⚠️ **早间批次盲区（2026-10-08实测修复）**：早间批次不采生产订单明细（detail层），restock-deep 读不到当日文件时在产=0，导致全部误判"追加下单"。**处置**：早间跑第2.5步前，先检查当日槽有无 yizhe_production_list.jsonl，没有则复制最近快照到当日槽再重跑 ingest+restock-deep（待把回落逻辑内置进脚本）。

**季节三分类**（season 字段 × 动销趋势：近7日均值 vs 前23日均值，阈值 ratio≥1.5=上行）：
| 分类 | 判定 | 动作 |
|---|---|---|
| 秋季上行 | season=秋季 且 ratio≥1.5（或前23日0销量新起） | 追加下单，量上调 30~50%（脚本给出区间下限~上限） |
| 档口预占 | 超卖 且 前23日零销量（近7日大额批单+负库存） | 净补**挂起**，先与档口确认是否已售待发——负库存大概率=预占而非真实零售缺口 |
| 冬季慢热 | season=冬季 且 近7日零动销（前23日有量） | 缓——10月中看华南档口上冬装节奏再定，**不必赌北方降温** |

**地区板块**（依赖 duoke_orders_30d.jsonl，缺失时跳过并提示）：三级地域解析 = province字段 → address文本（省名/城市名匹配）→ **客户名前缀**（行业惯例"城市+人名"如"芜湖杨婷"，识别主力）；输出省份Top10、气候大区分布（华南/华东/华中/西南/华北/东北/西北/海外）、周度趋势表。

**已验证的商业事实（2026-09-28）**：华南占57%（广东+福建）、北方合计仅约10%且4周无启动迹象 → 补货节奏由华南换季+十三行档口驱动，冬款看10月中档口上冬装，不看北方冷空气。订单列表接口**无商品行明细**，款级×地区交叉需逐单查详情（884单成本高，暂不做）。

**产出解读口径**：追加下单（含上调区间）> 催货（盯交期）> 核实档口（挂起等确认）> 缓（10月中再议）。周一定时批次采到 duoke_customers.jsonl（完整地址）后，可将识别率从~80%提到接近100%并复核本结论。

## 月度成本核算方法（2026-10-09 归档，可复用于任意月份）

**数据准备**（直连，复用 endpoints.json 端点改窗口参数）：
1. 复制 endpoints.json 为临时计划文件，改三处：duoke_orders/duoke_payments 的 sday/eday 改为月初/月末，yizhe_finance_sum 的 created_at 改为 [月初, 月末]；输出文件名加后缀（如 `_sep`）
2. ⚠️ 临时计划**必须保留原文件的 base_page/base_api/login_check 字段**（否则 fetch 报 "Failed to parse URL from undefined/..."）
3. 备份原 endpoints.json → 换入临时计划 → `fetch-endpoints.mjs --batch first --date <采集日> --slot pm` → 还原
4. 动销趋势：days=38 的接口会报9999客户端错误，改用**两份30日动销拼接**（月初前3天内采的一份 + 月末后采的一份，同日取新）；SKU成本价取最近商品快照（price_in 按库存加权，无库存取SKU均值）

**口径坑（必须向用户披露）**：
- 多客动销接口 = **出库日记账**：月末创建未发货订单（如9月6059件）不入当月动销 → 动销件数 < 订单净件数是正常现象，出库口径更真实反映当期成本
- 流水 type=1 收款(正)/退款(负)，type=3 核销调整
- 部分销量（9月为11.5%）对应款无成本价记录（多为已删档商品），实际成本略高于核算值，需披露上限
- 衣者采购单金额（如9月¥60.3万）与多客销售成本口径独立，不作强对平
- 订单 calc_price 正=销售、负=退货；订单净额−净收款=挂账/应收差额

**产出模板**：`out/成本核算-<年月>.md`（双口径对照表、实收现金流、品类/周度成本分布、口径说明、数据文件清单）

## 双系统库存差异比对（第2.6步，stock-diff.mjs）

**⚠️ 最重要的口径事实（2026-10-09 实测）**：衣者成品库存接口 `/common/stock_store/get_stock_list` 的 `total_num` **不是当前库存，而是累计入库件数**。证据链：
1. 09-28→10-09 共 1272 个同款中 **增 0 / 减 0 / 持平 1272**（真实库存11天不可能零变动）
2. 与多客在库件数款级相关系数 r≈0.19（近零相关，非同一口径）
3. 量级 67.9 万件 ≈ **32 个月**销量（多客30日动销仅 2.1 万件）
4. 老款数值最大（2025春一波 SK251173 达 7543 件、30日动销 0），新款量级正常

→ **禁止**把「衣者 67.9万 vs 多客 4.3万」当真实库存落差出结论；脚本会自动体检并告警。若要衣者当前库存：需在 /stock-list 页面确认列字段名（2026-10-09 该SPA页面未能渲染，evaluate 返回空 innerText），或修好出货记录端点后按「累计入库 − 累计出货」推算（当前 `yizhe_stockout_records` 返回 0 条，status_list/created_at 参数待自愈）。

**可比的部分**：多客在库（SKU `warehouse_0`，负数=超卖欠货）多时点序列、款级"有无库存"覆盖差异、超卖缺口 vs 衣者待入库。

**已知数据坑**：
- `data/raw/2026-10-08/pm/duoke_goods.jsonl` 与 `2026-09-28/am` **md5 完全相同**（成本核算时复制的副本，非独立快照）→ 多客有效时点只有 09-28 与 10-09；脚本已做 md5 去重并在表格标注「副本」
- 衣者款号常带后缀（`LC263789—河南郭清清`、`SQ242786/刻为`、`WT261397（套装）`）→ 比对前按 `[-—(（/]` 截断规范化，未匹配款从 25 降至 2
- 衣者成品库存接口 `only_has_stock=1`，只返回有库存款（1292/1452）
- 衣者入库单 146 单全部"待入库"（已入库 0），出货数 21,650 件——入库流程滞后，解释为何多客侧冬季新款已在售而衣者成品库无记录

## 款号人工核对回写（US-05）

1. `out/款号核对清单-<日期>.md` 生成后呈现给用户（两侧款号/款名/品类/季节对比）
2. 用户在对话中确认（例：「SK263967 对应 SM263967，确认」）或给出正确对应关系
3. 将 manual_queue 对应项写入 `state/mapping.json` 的 pairs（method: "manual"、confidence: 1、记确认人与日期），并从 manual_queue 移除
4. 后续采集自动命中，无需重复确认
